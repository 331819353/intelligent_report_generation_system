# DAG 智能建模统一工作流

> 状态：已实现统一状态机与前后端主链路。核心代码位于 `internal/datasetai/workflow.go`、
> `business_blueprint.go`、`blueprint.go`、`blueprint_context.go`、`session_service.go`，前端入口位于
> `web/src/pages/DatasetCenterPage.tsx`。

## 1. 定位与边界

AI 的定位是**建模副驾 + 变更规划器**，不是 DAG 执行器。

- AI 可以理解业务语言、检索业务知识、形成结构化意图、推荐数据范围、提出业务蓝图、物理蓝图和完整 DAG 候选图。
- AI 不直接改画布，不执行 SQL，不保存或发布数据集，也不能在修改任务中扩大用户授权的变更范围。
- 确定性程序负责状态推进、权限与目录裁剪、结构校验、字段血缘、模型分层约束、变更边界、原子落图、自动布局、预览和撤销。
- 用户确认是业务口径和数据范围的最终裁定；保存与发布始终是独立动作。

入口只有两个：

1. 画布完全为空：`CREATE`，走完整建模状态机。
2. 画布存在任意组件（包括未保存草稿）：`MODIFY`，以实时画布为基线走受限变更状态机。

不能用“数据集是否已保存”判断 CREATE/MODIFY；唯一判据是实时画布是否为空。

## 2. 对原始流程的校正

原始主干方向正确，但需要消除以下歧义。

| 原说法 | 统一定义 |
|---|---|
| 指标加工逻辑确认 | 选表前的 `METRIC_DEFINITION`：指标叫什么、统计什么、排除什么、时间口径是什么、是否来自已治理指标。 |
| 指标实现口径确认 | 选表后的 `METRIC_BINDING`：用哪些物理字段，以聚合、透传或派生计算的哪种方式实现。 |
| 事实表检索 | `PRIMARY_SOURCE` 主来源检索。DIM 找实体来源，DWD 找事实明细来源，DWS 优先找 DWD/事实来源，ADS 优先找已发布 DWS。 |
| 每一步都弹确认 | 每个阶段都留下决策记录，但只有新口径、低置信度、多候选或用户重新打开的阶段阻塞并要求确认。 |
| 维度表、关联必有 | 维度来源可显式跳过；只有确认范围超过一张表时 JOIN 才是必需阶段。 |
| ADS 等同汇总层 | ADS 可再次聚合，也可透传上游 DWS 指标，或对两个上游指标做确定的派生计算；不能一律强制 GROUP。 |

原流程还缺少三个不能省略的决策：

- `GRAIN`：最终每行代表什么；这是判断重复计数、关联扇出和输出正确性的前提。
- `OUTPUT`：最终输出字段、指标、名称和稳定 code；否则 END 节点会由规划模型自由发挥。
- 修改重入：修改不能重新生成所有口径，只能重入 changeSet 实际影响的阶段。

时间不是单独组件阶段，而是一条跨阶段约束：业务时间含义和粒度在 GRAIN 确认，物理时间字段在物理蓝图绑定，需要格式化时进入 TRANSFORM，需要范围限制时进入 FILTER。

## 3. 统一状态机

稳定阶段顺序如下。阶段可以 `SKIPPED`，但不能从审计轨迹中消失。

| 顺序 | 阶段 | 主要载荷 | DIM | DWD | DWS | ADS |
|---|---|---|---|---|---|---|
| 0 | `INTAKE` 需求理解 | goal、实体、度量、维度、时间表达、过滤意图、知识命中 | 必经 | 必经 | 必经 | 必经 |
| 1 | `KIND` 类型判断 | kind + KEYWORD_RULE / LLM_INTENT / USER_CONFIRMED | 必经 | 必经 | 必经 | 必经 |
| 2 | `GRAIN` 业务粒度 | 每行含义、业务粒度键、时间粒度 | 必经 | 必经 | 必经 | 必经 |
| 3 | `METRIC_DEFINITION` 指标定义 | 指标名称、完整业务定义、REGISTRY / NEW | 跳过 | 跳过 | 必经 | 必经 |
| 4 | `PRIMARY_SOURCE` 主来源 | 确认的 PRIMARY 表 | 必经 | 必经 | 必经 | 必经 |
| 5 | `DIMENSION_SOURCE` 维度来源 | 确认的 DIMENSION 表或明确跳过 | 可选 | 可选 | 可选 | 可选 |
| 6 | `JOIN` 关联关系 | 表对、键对、类型、基数、证据来源 | 多表必经 | 多表必经 | 多表必经 | 多表必经 |
| 7 | `METRIC_BINDING` 指标实现 | AGGREGATE / PASSTHROUGH / DERIVED | 跳过 | 跳过 | 必经且聚合 | 必经，模式按目标 |
| 8 | `TRANSFORM` 字段转换 | 组件类型、具体 operation、顺序输入、前/后聚合位置 | 可选 | 可选 | 可选 | 可选 |
| 9 | `FILTER` 过滤条件 | 字段、operator、valueMode、value | 可选 | 可选 | 可选 | 可选 |
| 10 | `OUTPUT` 最终输出 | 来源字段或指标、name、code | 必经 | 必经 | 必经 | 必经 |
| 11 | `GENERATE` 候选图 | 完整 GraphPlan，不是 SQL | 必经 | 必经 | 必经 | 必经 |

状态值统一为：

- `PROPOSED`：等待用户确认，阻塞后续受保护的状态迁移。
- `AUTO_CONFIRMED`：高置信且无等价候选，系统代为确认，仍可由用户重新打开。
- `USER_CONFIRMED`：用户确认或编辑后确认。
- `SKIPPED`：模型类型不适用或目标明确不需要，必须记录原因。

每项还记录 `source`、`confidence`、`reason` 和 `decidedAt`。新指标（`origin=NEW`）即使模型给出高置信度，也必须由用户确认；已治理指标只有在命中 registry code 且高置信时才可自动确认。

## 4. CREATE：空白画布的实际顺序

```text
打开会话
  → 解析自然语言与类型（规则优先；未命中时先取业务知识供 AI 分类兜底，仍不确定才询问）
  → 检索业务知识并生成 BUSINESS 蓝图
  → 确认业务粒度与指标定义
  → 按已确认业务意图检索并确认 PRIMARY 来源
  → 检索并确认 DIMENSION 来源，或显式跳过
  → 服务端合并并锁定表范围
  → 加载范围内授权表、字段、键与认证关系
  → 生成 PHYSICAL 蓝图
  → 确认关联、指标实现、转换、过滤和输出
  → 生成完整结构化 DAG 候选图
  → 确定性合规校验
  → 展示方案；用户继续对话调整或点击应用
  → 原子落图、自动布局、END 预览
  → 继续修改 / 撤销 / 保存 / 发布
```

### 4.1 为什么业务蓝图必须在选表之前

业务知识检索和结构化意图先确定“要做什么”，表检索再回答“哪些数据能实现它”。如果先让用户选表，现有字段会反向诱导模型改变粒度或指标定义。

`POST /sessions/{id}/intent` 因此只接收 goal、kind 和类型来源：

- 检索业务术语与已治理指标，不使用物理表范围；
- 产出 `StructuredModelingIntent`；
- 产出 phase=`BUSINESS` 的 GRAIN / METRIC_DEFINITION；
- 不允许命名表、字段、组件或生成 DAG。

BUSINESS 蓝图存在未确认项时，服务端拒绝表推荐和范围确认，客户端不能跳过这道门。

交互按阶段渐进展开：界面一次只展开最早的 `PROPOSED` 项，确认 GRAIN 后才展示适用的 METRIC_DEFINITION；已确认前序只保留为紧凑摘要，未来项不提前展示。规则判定不适用的阶段仍保留在服务端审计轨迹中，但不作为一张“已跳过”卡片打断当前确认。

### 4.2 为什么主来源和维度来源分两次确认

二者的检索目标和排序规则不同，合并成一张候选卡会让维表挤占事实来源名额，也无法表达“已确认主表，但不需要维表”。当前流程先确认 PRIMARY，再用同一份业务意图检索 DIMENSION；第二步允许明确选择“不使用维度表”。

表推荐请求携带 `sessionId + role`。服务端从会话读取可信的 goal、结构化意图、粒度和指标定义，客户端提交的普通 query 不能覆盖这些已确认决策。候选池先按角色检索再应用数量上限，不能先截取混合结果再在前端过滤；ODS 只是物理层级，事实/维度角色必须继续读取治理标签、业务名称与表名。维度检索还会把已确认事实表的声明外键目标作为确定性召回证据，并优先选择同一数据源中的目标表。前端保留服务端混合检索顺序，不再用第二轮关键词门槛删除向量或关系召回结果。确认范围后，规划目录严格裁剪为已确认表；`SourceDecisions` 分别记录 PRIMARY 与 DIMENSION 的确认/跳过结果。

资产标签化用于提升召回与排序，但不能替代结构化元数据。最小治理集合建议包括：模型角色（事实/维度/指标来源）、业务主题与过程、数据粒度、适用分析范围；字段侧补齐业务名称、说明和语义类型。主外键、认证关联、数仓层级应保存为专用结构化字段，不能只写成自由文本标签。没有完整标签时系统仍应依靠名称、说明、字段和声明外键降级工作，而不是退化成单结果。

标签分为两层：物理表标签是紧凑检索文档，按“作用、主题、过程、精确粒度、时间行为、范围”生成，并由声明主外键补充关联证据；DIM/DWD/DWS/ADS 数据集版本则从租户的 ACTIVE CONTROLLED 词表产生治理建议，只有已批准标签进入跨数据集检索。ODS 数据集版本同时继承来源物理表标签，避免映射为数据集后丢失原有主题和粒度。标签生成必须限制弱相关标签数量，复合粒度（如订单商品、售后工单）优先于多个宽泛实体标签。

### 4.3 物理蓝图

范围确认后，`POST /sessions/{id}/blueprint` 才加载表和字段元数据并生成 phase=`PHYSICAL` 蓝图。它必须继承 BUSINESS 蓝图：

- 指标定义不能在物理阶段被改写；
- 业务粒度描述、键和时间粒度不能被改写；
- 物理阶段只补充时间字段绑定，并在需要时重新请用户确认该绑定；
- 所有表与列引用必须落在确认范围中。

## 5. 四种模型的物理约束

### 5.1 DIM

- 每行一个实体，粒度键是实体业务键/主键。
- 可以单表，也可以关联 lookup 表，因此 JOIN 不是按模型类型禁止，而是按表数决定。
- 不生成 GROUP；数值属性仍是普通字段，不定义聚合指标。

### 5.2 DWD

- 每行一条业务事件或明细，保留可追溯的明细键和原始度量字段。
- 可以关联维表补充属性。
- 不生成 GROUP；“金额字段”是明细字段，不等于“销售额指标”。

### 5.3 DWS

- 每行是维度组合 + 可选时间粒度。
- 必须有指标定义、AGGREGATE 物理绑定和至少一个 GROUP。
- 聚合绑定只能使用 SUM / AVG / COUNT / COUNT_DISTINCT / MIN / MAX；SUM/AVG 的输入必须为数值字段。

### 5.4 ADS

- 每行是明确的展示或应用粒度。
- 指标实现必须逐项选择一种模式：
  - `AGGREGATE`：从明细或上游数据再次聚合，需要 GROUP；
  - `PASSTHROUGH`：直接使用上游已经计算好的指标列，`aggregation=NONE`，不强制 GROUP；
  - `DERIVED`：对两个有序数值输入执行 ADD / SUBTRACT / MULTIPLY / DIVIDE，使用 NUMBER_ARITHMETIC，不强制 GROUP，输入顺序必须与确认口径一致。
- 同一 ADS 可以混合上述模式；只要包含 AGGREGATE 绑定，就必须出现 GROUP。

## 6. MODIFY：非空画布的受限变更

```text
读取实时画布及版本指纹
  → 第一次 AI 调用只解析修改意图
  → 形成并锁定 changeSet
  → 目标不唯一时返回候选组件并询问用户
  → 用户答案结构化写入会话
  → 第二次 AI 调用只在 changeSet 边界内生成修改后完整图
  → 恢复所有未授权组件与字段
  → 比较当前图与候选图，拒绝越界差异
  → 展示本次变更与修改后完整流程
  → 用户确认后原子应用
```

规则：

1. 修改永远以请求发起时的实时画布为基线，包括未保存草稿。
2. 未写入 changeSet 的组件、字段、拓扑和数据集元信息从当前画布恢复；AI 不能“顺手优化”。
3. 生成期间画布发生手工修改时，版本指纹不一致，旧候选不得覆盖新画布。
4. 修改要求新增数据源时，只重入缺失来源确认；确认后继续原 MODIFY 请求，不切换成 CREATE。
5. 候选方案本身不立即改蓝图。用户应用后，程序从应用前后两张图推导实际受影响阶段并同步；撤销或丢弃不改变阶段决策。

确定性的重入关系如下：

| 图差异 | 重入/同步阶段 |
|---|---|
| 数据节点表或字段变化 | PRIMARY_SOURCE / DIMENSION_SOURCE、JOIN、OUTPUT，按实际依赖级联 |
| 关联键或关联类型变化 | JOIN；下游绑定、过滤、输出按依赖重新核验 |
| 分组维度变化 | GRAIN |
| 分组指标变化 | METRIC_DEFINITION、METRIC_BINDING |
| FILTER 变化 | FILTER |
| 其他转换变化 | TRANSFORM |
| END 输出变化 | OUTPUT |
| 仅名称或说明变化 | 不重开业务口径 |

例如“把客户关联改成 INNER”只授权相应 JOIN 变化；若候选图同时改变分组或输出字段，差异校验直接拒绝。

## 7. 澄清、会话与恢复

澄清不是任意聊天文本拼接，而是一个可恢复的状态转换：

```text
发现目标不唯一 → 返回问题 + 当前图中的候选组件
→ 用户选择组件或输入答案 → 结构化持久化
→ 重新执行原请求 → AI 使用已确认答案
```

会话持久化：

- 业务目标、结构化意图、模型类型及来源；
- BUSINESS / PHYSICAL 蓝图及逐阶段确认状态；
- 主来源与维度来源决策、最终确认表范围；
- 澄清问题和用户回答；
- 方案状态：STAGED / SUPERSEDED / APPLIED / REVERTED；
- 应用后预览的行数、告警和可用于下一轮的执行发现。

会话保存的是**决策历史**，不是候选图仓库。DAG 基线始终来自实时画布或数据集草稿；刷新后可以恢复对话与口径，但旧的待应用候选图不能直接继续应用。

## 8. 确定性校验与落图

CREATE 候选图在展示前依次通过：

1. 严格 JSON 和组件合同校验；
2. DAG 无环、输入存在、单一消费链与 END 可达性校验；
3. 表必须位于确认 scope，字段必须存在且大小写一致；
4. 字段血缘、转换输入、关联两侧、分组输入与输出来源校验；
5. DIM/DWD 禁止 GROUP，DWS 强制 GROUP，ADS 按指标绑定模式决定；
6. 已确认 JOIN 的表、键和类型逐项一致；
7. AGGREGATE 指标的列和聚合一致，PASSTHROUGH 指标必须直接到 END，DERIVED 指标的操作与有序输入一致；
8. 已确认转换的 componentType、operation 与输入一致；
9. FILTER 和 OUTPUT 逐项落实；
10. 校验失败只允许一次受限自动修复，修复后重新执行全部校验。

MODIFY 还必须通过 changeSet 授权边界和最终图差异校验。

应用前不改变画布；应用是整张图原子替换并自动布局。应用后执行 END 前 5 行预览，用户可以继续修改或撤销。保存、发布不由 AI 自动触发。

## 9. HTTP 主链路

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/datasets/ai/sessions` | 打开/恢复建模会话 |
| POST | `/api/v1/datasets/ai/intake` | 关键词未命中时，用授权业务知识辅助类型语义分类 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/intent` | 业务知识检索、结构化意图、BUSINESS 蓝图 |
| POST | `/api/v1/datasets/ai/table-suggestions` | 按 session 与 PRIMARY/DIMENSION 角色推荐表 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/scope` | 原子确认合并后的表范围与角色 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/blueprint` | 生成 PHYSICAL 蓝图 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/blueprint/revisions` | 在当前阶段边界内自然语言调整蓝图 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/stages` | CONFIRM / CONFIRM_ALL / SKIP / REOPEN |
| POST | `/api/v1/datasets/ai/proposals` | 生成 CREATE 或 MODIFY 候选图 |
| POST | `/api/v1/datasets/ai/sessions/{sessionId}/events` | 记录方案应用、撤销和预览结果（事件中携带 requestId） |

外层 API 路由必须显式暴露 intent、blueprint、revisions 和 stages；只在内部 handler 注册而未加入主路由会导致功能在单测可用、实际请求 404。

启用了会话存储的生产部署中，空画布调用 proposals 时 `sessionId` 是强制项；缺少会话会在调用规划模型之前被拒绝，从而不能绕过 BUSINESS、来源范围和 PHYSICAL 三道确认门。只有未配置会话存储的兼容部署保留 stateless CREATE。

## 10. 当前降级边界

1. 没有 ACTIVE semantic release 时，业务知识检索返回降级原因，流程仍可继续，但新指标必须由用户确认。
2. 原始物理表没有语义模型时，来源推荐依赖资产元数据、关键词/向量检索；关联候选依赖声明外键、认证关系和键名类型匹配。
3. 数据基数与扇出探测发生在应用后的预览阶段，不在每次蓝图确认时查询数据仓库；发现风险会重新打开 JOIN/FILTER 等受影响阶段。
4. 蓝图卡支持常用结构化编辑；复杂转换参数或跨阶段调整继续通过自然语言修订，并仍需经过相同的确定性校验。

这套协议的核心不变量是：**先固定业务语义，再选择能实现它的数据；先确认物理口径，再生成图；先验证候选图，再由用户决定是否落图。**

## 7. 证据驱动的判断环节清单（“像人一样”找表、对键、定口径）

原则：**不用相似度截断代替判断**。凡是需要“在很多候选里认出对的那个”的环节，都按同一套三步走：
① 全量分块初筛（模型逐张看卡片，只做“可能 / 不可能”）→ ② 入围细看（完整字段 + 几行真实样例，能对数据就对数据）→ ③ 仍拿不准就交给人，并把证据一起交出去。向量/关键词检索只用来**排序**分块顺序，不再决定谁被看见。

| # | 环节 | 人会怎么做 | 现在的实现 | 状态 |
|---|---|---|---|---|
| E1 | 主来源表（事实/实体/上游汇总）识别 | 翻遍所有表的名字和说明，挑出可能的几张，再打开看字段和几行数据，确认粒度、度量列、时间列；同名的 ODS/DWD 版本选发布层 | `screening.go ScreenSources(role=PRIMARY)`：全池分块（每块 24 张，最多 480 张）→ 入围 ≤10 张细看（字段 + 5 行脱敏样例）→ SELECTED/UNSURE/REJECTED；多张同时成立需模型说明 needsMultiple；否则交人 | ✅ |
| E2 | 维度表识别 | 拿着主表的外键去找“谁的主键长这样”，看几行数据的键格式/值是否对得上 | `ScreenSources(role=DIMENSION, anchors=已确认主表)`：同样分块；细看阶段服务端先按键名/类型算候选键对，再用样例值比对（`sampleKeyCompatibility`：值重叠 → SAMPLE_MATCH；同为数字且长度接近 → COMPATIBLE；一边数字一边带前缀文本 → FORMAT_MISMATCH）；模型给 joinHints，服务端用样例证据否决过于乐观的选择 | ✅ |
| E3 | 关联键确认 | 先看声明外键 / 已认证关系，其次同名键，最后看两边样例值 | 蓝图 `joinCandidates` 带 provenance（FOREIGN_KEY / REGISTRY / NAME_MATCH）与 `sampleCompatibility`；FORMAT_MISMATCH 要求换键或先 CAST/TEXT 对齐 | ✅ |
| E4 | 过滤条件字面值 | 先看这一列实际存的是 `2`、`PAID` 还是 `已支付`，再写条件 | 蓝图 envelope 携带每张物理表 5 行脱敏样例；规则 3a 要求按样例中的实际编码写字面值，样例未见目标值时降低置信度交人确认 | ✅ |
| E5 | 时间列与格式 | 看样例判断是日期型还是文本日期 | 同上（规则 3a），文本日期要求 CAST | ✅ |
| E6 | 度量列选择与单位 | 看样例是否有负数、单位是分还是元 | 同上，写入 `metricBinding.note` | ✅（提示级） |
| E7 | 同一业务表的多版本去重 | 优先发布层、字段更完整的版本 | 细看提示词规则 2；候选池对物理表按逻辑名去重、保留发布版本 | ✅ |
| E8 | 粒度核验（每行一条什么） | 主键 / COUNT DISTINCT 探针 | 声明主键进入卡片与蓝图；真正的 COUNT DISTINCT 在应用后的预览由查询运行时探测并回灌（§5） | ✅（应用后） |
| E9 | 宽表（>60 列）的字段选择 | 分页看字段 | 细看卡片截到 60 列；超宽表尚未分块看列 | ⚠️ 未做 |
| E10 | 类型判断歧义 | 说不清是明细还是汇总时问一句 | 规则 → LLM → 类型卡 | ✅ |
| E11 | 主表间关系（订单头 ↔ 订单行） | 多张主表并存时确认关系与粒度 | 细看阶段允许多选并要求说明；关联在蓝图 JOIN 阶段确认 | ✅ |

新增接口：`POST /ai/sessions/{id}/sources/screen {role, anchorTableIds, excludeTableIds}`（进度流：逐块进度 / 细看 / 结论），结果存于 `session.state.sourceScreenings[role]`（入选 + 待定 + 理由 + 关联键证据），前端候选表卡直接展示“入选理由 / 拿不准需要你判断（纳入）”，无需人工时自动进入下一环节。样例数据经 `internal/datasetai/sampling` 走资产预览同一条受控路径（≤5 行、敏感列隐去、无客户端 SQL），发布版本没有样例时明确标注“仅凭元数据”。

成本：每次筛选 = ⌈候选池/24⌉ 次初筛调用 + 1 次细看调用；480 张表约 21 次小调用。候选池上限触顶时标注 `truncated`。
