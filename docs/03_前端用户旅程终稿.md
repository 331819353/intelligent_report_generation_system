## 1. 文档目标

本文把 P01～P14 的模块级业务流程拆到可直接设计页面的操作级用户旅程。每条旅程必须明确：谁在什么条件下进入、从哪里进入、依次看到/输入/确认什么、系统在同步/异步/成功/部分成功/失败时如何反馈、权限/版本/口径/数据变化时如何恢复、操作何时结束、产物在哪里、哪个角色接棒。

### 1.1 一期旅程裁定

一期页面和 E2E 按资产依赖实施，不按导航排列顺序实施：

```text
P11 报告设计、校验、发布
  -> P12 报告资产认证与投影
  -> P09/P10 对话检索并引用已有报告版本/组件
```

智能报告和智能问数都必须让用户感知 LLM 正在完成「识别—分析—规划—指派」，但只展示结构化计划、工具动作、证据和结果，不展示隐藏思维链。

## 2. 完整旅程的验收口径

每个旅程编号必须在需求、设计稿和 E2E 中交付：角色（发起/处理/审批/Owner/只读）、入口、前置条件、主操作、系统反馈、异常恢复（校验失败、409、403、失效、超时、断线、部分成功、重试）、终态、下游。只有一张「正常状态页面」不算完成。

实现状态标识：`REAL`（真实 API 主链）/ `PARTIAL`（有页面或 API 但有静态数据或缺关键分支）/ `BE-ONLY`（后端就绪无页面）/ `NEW`（前后端均需新增）/ `BIZ-GATE`（需业务确认）。

## 4. 目标信息架构与页面责任

### 4.1 一级导航

导航以 [web/src/components/AppShell.tsx](../web/src/components/AppShell.tsx) 为事实源，当前分三组：

```text
业务工作      分析首页 / 问数工作台 / 报告中心
```

导航只暴露已经可用的页面：未交付的入口不做成常驻的禁用占位项，避免用导航规模冒充交付进度。

全局顶栏提供当前领域、通知、帮助和用户菜单。领域切换是全局上下文变化，不是普通筛选器。跨模块的执行类待办以「通知 + 各模块内待办」承载；统一任务中心为后期规划。

## 5. 全局交互规则

### 5.1 所有页面必须设计的状态

首次加载（骨架）、首次空态（唯一主行动）、筛选无结果、保存中（锁写）、异步处理中（任务 ID/阶段/取消）、成功（产物+审计+下一步）、表单校验失败（就地+页级摘要）、409 版本冲突（刷新/差异/放弃，禁止强制覆盖）、403 无权限（解释+申请路径，不泄漏对象）、404/已下架（区分不存在/下架/无权）、部分成功/降级、数据/口径漂移（显式确认重放）、网络断开（保留输入、事件游标续传）、可重试失败（安全错误码）、不可重试失败（失败关闭+出口）、危险操作（影响+原因+二次确认）。

### 5.2 通用操作模式

新建（先草稿/向导）、保存草稿（版本号+离开保护）、提交审批（先本地校验）、撤回（仅发起人待审时）、通过/驳回（驳回原因必填）、发布/激活（不可变版本+门禁+下游影响）、回滚（不改写历史）、下架/归档（影响清单+原因必填）、恢复/上架（重新校验）、分享（受权主体+有效期，链接不提权）、导出（格式/范围/数据时点/敏感说明，大任务异步）、删除（仅未发布无引用草稿）、取消异步任务（明确可取消性与中间结果）。

### 5.3 权限展示规则

- 导航按角色隐藏无关治理入口，但无权深链接必须返回受控 403 页面。
- 对象操作以服务端 `allowedActions` 为准；前端不根据角色名自行推导。
- 会泄漏对象存在性的动作直接隐藏；有解释价值的动作可禁用并说明。
- 双人审批必须显示「仍需另一位审批人」；审批人不能伪装成申请人。
- 领域切换后清理领域内缓存并重载当前路由；编辑态先提示未保存内容。

### 7.1 一期主旅程：报告先行到对话引用

```mermaid
flowchart LR
    A["报告作者定义目标和受众"] --> B["LLM 识别/分析/规划/指派"]
    B --> C["设计器校验并发布"]
    C --> D["报告资产认证/投影"]
    D --> E["业务用户在智能问数提问"]
    E --> F["LLM 检索并分析报告资源"]
    F --> G["指派报告运行/语义查询工具"]
    G --> H["答案展示报告版本/组件来源卡"]
    H --> I["打开来源/继续追问/反馈"]
```

每次交接都必须保留报告版本、组件、Hash、Owner、权限和来源链接。

### 7.2 报告作者：周期经营报告

模板/空白/复制 → LLM 识别/分析/规划/指派 → 画布与绑定 → 筛选/证据/结论 → 查看者权限预览 → 发布不可变版本 → 分享/导出 → 从报告发起问数 → 新周期复制修订、重新验证和发布。

### 7.3 数据与语义 Owner：从数据接入到可问可报

数据源草稿/测试/审批 → 元数据发现与资产完善 → 数据集建模/发布/物化 → 语义模型/指标/维度/词典建设 → Release 投影/评测/双人审批/激活 → 问数和报告使用 → 反馈/结构变化 → 新草稿/回归/灰度/回滚。

### 7.4 运营人员：错误反馈到用户确认

结构化反馈 → 去重分诊回放 → 归因 → Owner 接受修复候选 → 原问题+专项+密封回归 → 发布与灰度 → 通知原用户 → 确认或重开 → 复发率与修复价值复盘。

### 7.5 运维人员：告警到业务恢复

告警聚合 → 事件确认 → 限流/熔断/切换/失败关闭 → 恢复服务 → 重放受影响运行 → 业务 Owner 验证 → 关闭事件 → 根因与改进。

## 10. 前端设计顺序

1. 报告资产中心、新建向导和 LLM 报告引擎状态。
2. 报告设计器、数据绑定、证据/结论、预览、发布和版本。
3. 报告运行时、报告资产认证/投影及来源可用性状态。
4. 智能问数主链中的报告检索、版本/组件来源卡、受权跳转和继续追问。
5. 全局 App Shell、分析首页、领域切换、真实历史、保存/反馈和通用状态。
6. 语义中心、Release/评测、反馈运营和观测治理页面。
7. 用 §7.1 旅程完成一期 E2E；fixture 不得用于签署。

后期规划旅程（决策中心、问数写回报告、任务中心、订阅分发）在一期签署后按 [04 §8](./04_实施规划与验收终稿.md) 推进。设计阶段每完成一个页面组，必须回到对应 J-Pxx-xx 做覆盖检查。
