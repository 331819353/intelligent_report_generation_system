## 1. 架构原则

1. PostgreSQL 是语义、版本、权限和审计的唯一事实源。
2. pgvector 和 NebulaGraph 均为可重建投影。
3. LLM 是系统的认知与决策中枢，负责理解用户意图、任务规划、能力选择、流程编排决策、结果判断与自然语言交互，但不能绕过权限、版本、工具和编译器。
4. 智能报告和智能问数共用「识别 → 分析 → 规划 → 指派」的 LLM 引擎阶段协议；LLM 指派工具，不直接执行副作用；数据处理、计算、查询和业务执行由专业化 Skill、Tool 和传统软件服务确定性完成。
5. SQL 只能由 Semantic IR 经 Go 编译器确定性生成。
6. 问数首期只访问 ACTIVE DWS/ADS。
7. 查询和报告运行使用当前阅读者权限。
8. 所有生产对象固定不可变版本和内容 Hash。
9. 低置信问题必须继续取证、澄清或阻断。
10. 报告 Definition、Question Artifact、Query Plan、Evidence 均可回放。
11. 一期对话只能引用已存在、已发布且当前用户可见的报告资源；不得静默创建/修改报告。
12. 95% 通过密封 E2E 评测和发布门禁证明。
13. 能力依赖链固定为：数据建模 → 语义建模 → Release ACTIVE →（报告 | 问数）；报告与问数是语义层的同级消费者，报告资产仅为问数的增强先验，不是问数的前置条件。

## 2. 执行链路架构

```text
User
  │
  ▼
LLM（认知与决策中枢）
  ├── Intent Recognition   意图识别
  ├── Planning             任务规划
  ├── Tool Selection       能力选择
  ├── Context Management   上下文管理
  └── Result Evaluation    结果认知判断
          │
          ▼
      Skill Layer（专业化能力层）
  ┌──────────┬──────────┬──────────┬──────────┐
  │ SQL      │ API      │ RAG      │ Analysis │
  └──────────┴──────────┴──────────┴──────────┘
          │
          ▼
Deterministic Systems（确定性系统）
```

### 2.1 层与平台组件映射

| 链路层 | 职责 | 平台组件 |
|---|---|---|
| LLM / Intent Recognition | 问题意图、资产类型识别（识别） | 问题理解与会话（M11）、报告引擎 IDENTIFY |
| LLM / Planning | 取证路径、报告结构与分析方法规划（分析+规划） | Agent Planner（M15）、报告引擎 ANALYZE/PLAN |
| LLM / Tool Selection | 选择并指派 Typed Tools（指派） | Tool Host（M15）、报告引擎 DISPATCH |
| LLM / Context Management | 会话继承（只继承已认证绑定）、Release 漂移确认、报告种子上下文 | M11 会话、M16 证据工作台 |
| LLM / Result Evaluation | 认知层结果判断：是否答题、是否纠错/澄清/降级 | Loop 自我纠错；**不替代**确定性校验 |
| Skill / SQL | Semantic IR → Query DSL → 方言 SQL → 有界执行 | 联合绑定（M12）、编译器（M13）、执行验证（M14） |
| Skill / API | 报告实例化、报告运行、资产读取、取数申请等平台服务 | 报告引擎、Report Runtime、平台 API |
| Skill / RAG | 语义对象与报告资产混合检索、图取证 | 混合检索（M09）、NebulaGraph（M10）、报告资产投影（M17） |
| Skill / Analysis | 受控分析方法、Evidence Bundle、智能结论 | Insight Engine、叙述事实校验 |
| Deterministic Systems | 最终裁决：权限、版本、门禁、编译、审计 | M01 权限、M08 发布、Orchestrator、数仓 |

### 2.2 Agent Loop 角色划分

```text
LLM Planner（认知与决策中枢）
  理解用户意图、任务规划、能力选择、流程编排决策、
  结果的认知层判断与自然语言交互；只决策，不执行副作用

Typed Tools（专业化 Skill/Tool/传统服务）
  执行数据处理、计算、查询和业务动作，
  返回真实、受权限控制的证据

Rules/Policies
  负责不可绕过的门禁与最终裁决

Orchestrator
  保存状态、预算、进度和终止条件
```

冻结的工具合同：

```text
search_semantic_objects / get_semantic_contracts / lookup_dimension_values
get_certified_examples / resolve_graph_plan / validate_semantic_bundle
get_data_quality_status / compile_semantic_query / validate_query_plan
probe_join_cardinality / execute_query_plan / execute_validation_query
compare_candidate_results / request_clarification
+ 报告侧：report_asset_search / report_component_runtime / report_instantiation 工具族
```

工具**名称与集合**冻结；结果结构在与存储事实冲突时按下述规则修订，并在本节登记：

| 变更 | 原合同 | 现合同 | 理由 |
|---|---|---|---|
| `get_certified_examples` | `CertifiedExampleSummary` 返回完整 `SemanticIR` + `semanticIrHash` | 返回期望绑定的组件：`expectedMetricVersionIds`、`expectedDimensionVersionIds`、`expectedTimeExpression`、`contentHash` | `askdata.certified_example_versions` 只存期望组件，schema 中不存在任何 IR 列；返回 IR 只能在读取时凭空合成。且认证问法是**检索先验**，必须由绑定阶段针对当前 Run 固定的 Release 重新解析，不能重放一份可能引用已被取代对象版本的冻结计划。 |
| `compile_semantic_query` | `CompileSemanticQueryResult` 只返回 `planHash` | 增加 `semanticIrHash` | 运行的受治理哈希链要求在 `IR_READY` 上登记 Semantic IR 哈希（[§2.3](#23-question-run-状态机)、`RunHashes.completeAnswerChain`）。该哈希必须来自**规范化并校验了 IR 的编译器本身**，不能由编排层重算——重算等于用一份编译器从未见过的 IR 去认证运行。工具因此不获得任何新副作用：只是把编译器已经计算出的 `QueryArtifact.IRHash` 暴露出来。 |

修订工具结果结构时：必须同步更新 `ValidateResult` 的边界校验（对象集合有界、标识规范、文本长度受限），并保证工具不会因此获得任何新的副作用能力。

### 2.3 Question Run 状态机

```text
RECEIVED → AUTHORIZED → CONTEXT_READY → UNDERSTANDING → RETRIEVING
  → BINDING → GRAPH_VALIDATING → IR_READY → PLAN_VALIDATING
  → EXECUTING → RESULT_VERIFYING → ANSWER_VERIFYING → ANSWERED

分支：UNDERSTANDING/RETRIEVING/BINDING/GRAPH_VALIDATING → CLARIFICATION_REQUIRED
     PLAN_VALIDATING/RESULT_VERIFYING → BINDING（有界纠错）
     UNDERSTANDING/BINDING → OUT_OF_SCOPE；RECEIVED/AUTHORIZED/EXECUTING → BLOCKED
```

`ANSWER_VERIFYING`：叙述生成后抽取全部数值和对象名，与 Result Artifact 和绑定合同逐项比对；比对失败重生成，连续两次失败降级为纯结构化答案。

### 2.4 Loop 预算

| 项目 | 上限 |
|---|---:|
| LLM 调用 | 4 |
| Tool 调用 | 8 |
| 正式查询 | 2 |
| 验证查询 | 3 |
| 候选计划比较 | 2 |
| 总耗时硬熔断 | 25 秒 |
| Join hops | 4 |

复杂 Loop P95 目标 ≤18 秒，Fast Path P95 ≤8 秒；等待澄清不计入预算，用户应答后恢复剩余预算。

## 5. 语义层关键合同

- **三类模型层必须区分**：数据集模型（物理/加工）、语义模型（业务实体与关系）、LLM 认知（不落库、不成为事实）。
- **指标 Formula AST**：类型化表达式（如 `DIVIDE(gross_profit, NULL_IF(sales_revenue, 0))`），编译期做除零/空值/单位/可加性校验。
- **时间口径**：未结束周期为 MTD；同比环比区间对齐；时区固定合同；数据可用边界显式。
- **可加性**：ADDITIVE/SEMI_ADDITIVE/NON_ADDITIVE 三分类 + 不可加维度声明；未确认可加性的指标不得进入首个 Release。
- **业务补充信息（Business Context）**：指标口径的业务说明、维度值定义与组织信息映射、企业内部黑话/缩写（业务词典条目，含负向上下文）、数据过滤规则（指标默认过滤 Filter AST + 行级安全过滤策略）。均为版本化受治理对象：模板采集/批量导入 → Owner 认证 → 随 Release 发布；作为检索文档与 LLM 上下文证据消费，不直接成为绑定事实（任务 SEM-CTX-001）。
- **数据质量规则（Quality Rule）**：是**绑定**而非表达式语言。`rule_ast` 只能是
  `DATASET_QUALITY_BINDING`，指向物化链路已经在执行的检查（执行目录见
  `internal/materialization`，为唯一事实源），语义层只读结果、绝不自行求值。
  求值时机为产出物化的数据集构建运行；结果针对语义模型经 `materialization_id`
  固定的 ACTIVE 物化，与查询实际读取的快照一致。绑定到不被执行的检查在写入、
  认证与 Release 门禁三处拒绝——受治理但无人可执行的规则，比没有规则更有害，
  因为它会把「从未检查」呈现为「检查未通过」。
- **Release 状态机**：`DRAFT → SEALED → PROJECTING → READY → ACTIVE → SUPERSEDED → RETIRED`；被历史资产引用的 Release 进入 RETAINED。
  取代在线 ACTIVE Release 的候选还须持有一份对照为当前 ACTIVE 的已接受 Shadow/Canary；
  业务域的首个 Release 无对照也无可切分流量，因此不要求灰度。

## 6. 报表作为问数资产

### 6.1 数据绑定两类模式

| bindingMode | 内容 | 可否反哺问数 |
|---|---|---|
| `SEMANTIC_IR` | 引用认证指标/维度/成员版本，固定语义发布 | 是 |
| `DATASET_FIELD` | 直接引用已发布 Dataset Version 字段 | 否 |

编译器拒绝：同组件双绑定、引用已退役 Release、同图表混合不可比单位/币种。

### 6.2 报告资产投影

报告发布时提取标题/章节目的/组件 Semantic IR/指标/维度/成员/图表模板/叙述角色/原问法，生成 `REPORT_ASSET` 检索文档与 `REPORT_VERSION/REPORT_COMPONENT` 图顶点及 `USES_METRIC/GROUPS_BY_DIMENSION/FILTERS_MEMBER` 边。

### 6.3 使用规则

报表资产只能是候选证据：不直接复制历史 SQL、不绕过当前 Release 与查看者权限、不自动使用历史自由文本结论；绑定过期降权或拒绝复用；答案引用固定 `reportId/reportVersionId/componentId/contentHash` + Semantic Release + 数据时点 + Evidence；撤权/下架/Hash 漂移时标明失效，不静默替换来源。

### 6.4 报告引擎（配置化报告）

- **Report Definition DSL V1**：页面/章节/分块/区域/槽位/组件树 + 数据绑定 + 筛选联动 + 主题；规范化后产生稳定 Hash。
- **Report Operation V1**：所有修改（人工与 AI）统一为类型化 Operation 差异，基于 baseRevision 乐观锁应用；LLM 不直接覆盖报告 JSON。
- **Component Manifest**：组件类型/图表模板注册，声明数据合同与布局约束。
- **发布编译**：草稿 → 发布检查（绑定/权限/布局/叙述校验）→ 不可变版本 + 制品；回滚生成新指针或新草稿，不改写历史。
- **运行时**：按当前查看者权限加载 Definition，规划并发执行组件；单组件失败不拖垮全报告；筛选变更只刷新受影响组件。
- **Insight Engine**：从组件 Evidence Bundle 生成智能结论，事实校验失败降级为结构化事实。

## 7. 存储与工程结构

- **PostgreSQL**：`platform` / `askdata` / `report` schema；语义事实、版本、权限、审计、评测、队列（Outbox + lease）。
- **对象存储（MinIO）**：报告制品、导出制品、大型 Manifest/评测工件；只接受数据库已引用且 Hash 一致的对象。
- **NebulaGraph / pgvector**：可重建投影。
- **Go 单体 + Worker**：`internal/{auth,access,datasource,asset,dataset,materialization,askdata,report,...}`；`cmd/{api,worker,...}`。
- **React SPA**：`web/src`；页面按路由分块，生产 JS 主块预算见性能设计。
- **API**：REST + SSE（Question Run 进度事件游标可断线恢复）；写操作幂等键；409 冲突返回差异。

## 8. 安全设计

- 检索前、绑定前、执行前三重权限裁剪；候选不泄漏无权对象存在性。
- 敏感成员仅 Hash 精确匹配；不进入 LLM、向量服务与日志。
- 提示注入防御：用户输入不作为可信绑定；客户端对象 ID 不作为可信引用；报告自由文本不进入语义事实。
- 密钥不回显；审计不可变；跨租户强隔离（RLS）。

## 9. 可观测性与成本

统一 Trace（Question Run / Report Run / 投影 / 物化 / 导出 / 评测），Run ID 可定位 Artifact 与上下游影响；按租户/领域/用户/功能归集成本与配额，80% 提示、100% 阻断高成本新运行；容量阈值告警不自动改变生产拓扑。

## 10. 95% 正确率的证明方式

1. 四级评测集：Development（构建期）、Validation（阈值调优）、Sealed（密封，正文不可见）、Security（越权/注入/敏感）。
2. 门禁指标从数据库事实重算：观测正确率 ≥96%，Wilson 95% 下界 ≥95%，P0 与安全样本 100%。
3. LLM 可生成评审摘要，但门禁结果必须确定性重算。
4. 密封集分片轮换与曝光退役；误差预算对账。
5. 新 Release 先 Shadow/Canary，回归失败停止扩容并回滚。

## 11. 测试与部署

- 测试金字塔：Go 单元/合同测试（`go test ./...`）、前端单元/契约测试、真实 PostgreSQL/Nebula 集成测试、密封 E2E 评测。
- 部署：Docker Compose（开发）；生产拓扑由容量 POC 签署后确定（见 [04_实施规划与验收终稿 §6](./04_实施规划与验收终稿.md)）。
- 灾备：控制库整体一致恢复点、对象存储 Hash 校验、投影重建收据；备份「成功」不等于恢复「验收」。

## 12. 最终验收门槛（技术）

1. 全部生产查询由编译器生成，LLM 零直接 SQL。
2. Release 投影 Hash 全一致才可运行；不一致失败关闭。
3. 所有生产对象不可变版本 + 内容 Hash，可回放。
