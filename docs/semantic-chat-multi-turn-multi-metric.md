# 多轮、多指标智能问答落地说明

## 已落地目标

智能问答采用与 ChatGPT/Codex 类似的“理解 → 规划 → 调用受控工具 → 观察结果
→ 生成答案”结构，但每一步只消费平台已治理资产：

```text
当前问题 + 前两次用户问题（临时三轮窗口）+ 上一轮已验证 QueryPlan IDs
  -> Jieba/HMM 分词 + 整句/逐词语义向量召回
  -> LLM 只在 Top N 候选内选择意图、指标和维度值
  -> 组合语境并按“当前轮同维度优先”形成完整意图
  -> 指标目录复核（支持一句话 1~8 个指标）
  -> 每个指标生成独立 QueryPlan
  -> 指标范围内解析维度和维度值
  -> 锁定精确指标版本、数据集版本、ACTIVE 物化和上游血缘
  -> 全部计划通过后执行
  -> 答案正文展示检索与校验过程
```

单指标 `POST /api/v1/semantic-qa/query-plans` 保持兼容。问答页面使用新的
`POST /api/v1/semantic-qa/query-turns`，一个轮次返回多个独立计划。执行仍调用
原有 `query-plans/{id}/execute`，因此权限、水位、版本、维度兼容、物化和血缘
门禁不会因多指标编排而降低。

## 多轮语义

- 上一轮只有状态为 `READY` 或 `EXECUTED` 的计划可以成为上下文。
- 当前问法没有明确指标时，继承上一轮全部指标。例如上一轮查询“销售额和订单量”，
  “那上个月呢？”会为两个指标分别重建时间窗口和计划。
- 当前问法明确了新指标时，新指标替换旧指标。
- 出现“再加、加上、以及、同时、还有、also”等追加语义时，新旧指标合并并去重。
- 上下文从上一轮持久化条件文档中恢复受治理的指标编码、领域、维度编码、
  `memberKey / memberKeys`、维度值候选选择轨迹和时间范围，不继承结果行。
- 客户端另传最多两个 `priorQuestions`，只用于本次返回中展示三轮原始语境；
  原始问句不写入 QueryPlan。条件继承仍只相信 `contextQueryPlanIds` 指向的
  已验证计划，防止用自然语言历史绕过治理门禁。
- 当前轮新增维度条件会替换同维度的旧条件，未提及的旧条件继续生效。例如先问
  “80后小微在职人员有多少人”，再问“其中的关键人才有多少”，第二轮计划同时
  保留出生年代段和在岗条件，并追加关键人才条件。
- 一轮任一指标未通过门禁时，页面不执行其他指标并明确列出失败原因，避免用部分结果
  回答完整问题。

请求示例：

```json
{
  "question": "那上个月呢？",
  "timezone": "Asia/Shanghai",
  "priorQuestions": [
    "本月销售额和订单量分别是多少？"
  ],
  "contextQueryPlanIds": [
    "上一轮销售额计划 ID",
    "上一轮订单量计划 ID"
  ],
  "maximumPathHops": 8
}
```

## 语义资产如何参与解析

`semantic_term_assets` 已接入两个受限入口：

1. `knowledgeType` 为 `METRIC / METRIC_ALIAS / 指标 / 指标别名` 时，
   `mappingValue` 必须等于已发布指标名称或编码。常用词只帮助召回，最终仍由
   `PUBLISHED` 指标版本确认。
2. `knowledgeType` 为 `DIMENSION_MEMBER / DIMENSION_VALUE / 维度值 / 维度成员`
   或等于具体维度名称/编码时，`mappingValue` 可等于成员规范值、成员键、正式名称
   或有效别名。映射结果还必须通过当前指标的 `VERIFIED`、非 `UNSAFE` 维度兼容边
   和成员有效期校验。
3. 一个业务词可以显式映射到逗号分隔的同维度成员集合。例如
   `80后 -> 80-85,85-90`。集合在查询层编译成一个参数化 `IN`，不会错误地生成
   两个互相冲突的 `EQUALS` 条件；集合中每个成员仍逐项进入证据链。
4. 对源字段中以逗号保存多个标签的维度，使用显式
   `TAG:<规范标签>` 合同。例如 `关键人才 -> TAG:关键人才`。服务端只在该维度
   当前有效成员中按完整标签边界展开，再将展开结果编译成参数化 `IN`；不会把
   `CONTAINS`、通配符或自由 SQL 带入执行层。单个受治理集合最多 128 个成员。

语义资产不能直接给出 SQL、数据集或结果，也不能跨指标/跨租户选择维度成员。

## “80后小微在职人员有多少人”资产合同

生产资产必须满足：

| 资产 | 必要条件 |
| --- | --- |
| 明细事实 | `dwd_enterprise_employee_base_info` 提供出生日期、人员状态与小微归属 |
| 汇总数据集 | `dws_employee_profile_regenerated_20260727` 按员工画像属性聚合；每条记录均有有效 `xiaowei_code` |
| 指标 | `员工总人数` 已发布并绑定精确 PUBLISHED DWS 版本 |
| 维度 | 原名“赛道”的字段实际存放出生年份段，语义维度已纠正为 `birth_cohort / 出生年代段`；另使用 `employee_status / 人员状态` 与 `xiaowei_code / 小微编码` |
| 维值 | `80后 -> 80-85,85-90` 是受治理集合；`在职 -> 在岗` 是受治理同义映射 |
| 多标签维值 | `关键人才 -> TAG:关键人才`，在 `key_talent / 关键人才` 维度中展开为 54 个包含完整“关键人才”标签的有效组合 |
| 语义词 | `小微在职人员`、`小微人员` 映射到已发布员工人数指标 |
| 兼容关系 | 出生年代段、人员状态和小微编码与指标版本均为 `VERIFIED + SAFE` |
| 物化 | 精确 DWS 版本存在同 schema hash 的 ACTIVE 物化 |
| 血缘 | 已证明 `SOURCE -> dwd_enterprise_employee_base_info -> dws_employee_profile_regenerated_20260727 -> METRIC`，且语义图水位已追平 |

当前本地真实物化表包含 810,289 个画像组合行。受控查询返回 `35,386`，页面答案为：

```text
查询结果：在小微人员范围内，按出生年代段为 80后（80-85、85-90）、
人员状态为 在职（映射为在岗）的口径，员工总人数为 35,386。
```

答案下方默认展开六步真实过程：

1. 展示最近三轮原始问题和由最终治理条件形成的独立问题；
2. 展示识别意图、指标词和维度值词；
3. 展示指标目录的实际候选、命中词、匹配方式和选中项；
4. 展示每个维度值的候选成员、映射方式、来源和实际选择；
5. 展示最终指标字段、维度字段、成员键、指标版本、数据集版本和血缘门禁；
6. 展示执行值、行数、耗时以及权限/版本/兼容性复核。

这六步直接渲染 `query-turns.trace`，不再由页面根据最终条件反推说明。旧计划缺少
轨迹时，页面明确标记“不可审计”，不会显示伪过程。敏感维度只显示候选数量和
选择状态，不展示成员值。右侧继续显示最低路径置信度、兼容性和完整证据链。

维度值步骤采用固定展示合同：

```text
维度字段：维度值
  -> 指标物理字段
  -> 业务 WHERE
  -> 安全编译 WHERE
```

服务端从语义维度资产取得字段名和字段描述，把已治理的
`字段描述 + 用户维度值` 作为向量查询，在当前已选指标的
`VERIFIED + SAFE` 维度范围内检索成员；再按成员有效期、非空成员键、集合上限
和指标兼容关系过滤异常候选。向量只负责召回，最终成员仍以精确语义资产、
正式别名或标签合同为准。

候选确定后，服务端把字段名、字段描述、用户值、匹配方式和已选择的非敏感
治理值交给 LLM。LLM 只能设计 `EQUALS / IN / CONTAINS` 操作符，不能输出 SQL
或新值；服务端逐项复核字段和值白名单，并把通过的决策编译为参数化条件。
LLM 未配置、失败或输出不合规时会明确记录回退状态，不能伪报模型设计成功。
敏感维度不会发送给向量或 LLM 服务。

例如关键人才：

```text
字段名：key_talent
字段描述：标识员工是否被评定为关键人才
向量键：标识员工是否被评定为关键人才:关键人才
  -> field_group_1_metric_t1_field_2
  -> LLM: CONTAINS
  -> key_talent LIKE '%关键人才%'
  -> field_key_talent IN (:key_talent_1 … :key_talent_54)
```

第一条 WHERE 是面向业务用户的等价表达；最后一条才是实际执行条件。执行层不
接受自由 SQL，也不直接执行裸 `LIKE`，而是把完整标签展开为 54 个当前有效、
已治理成员并使用参数化 `IN`，避免“非关键人才”等子串误命中。不同维度条件用
`AND` 拼接；同一语义集合在一个 `IN` 内合并，不能错误地把集合成员用 `AND`
连接。这里的“异常值过滤”指候选映射异常过滤，不会按最终指标数值自动删除
统计异常点，从而改变人员总数。

DWS 发布后，后台会先为每个 `VERIFIED + DIRECT + SAFE` 的“维度—指标—物化表”
关系生成一条字段级 WHERE 策略，再批量处理该维度下全部非空、有效、可语义化
成员。每个成员都以 `维度描述:规范值` 作为向量输入；成员语义文档与决策图共用
同一向量，不重复保存大向量。LLM 只决定该维度使用 `EQUALS` 还是
`CONTAINS`，服务端再逐成员生成受控业务 WHERE 和参数化执行条件。

预计算关系以 `DWS_PRECOMPUTED` 写入
`platform.dimension_where_decisions`；真实问答执行成功后会把同一关系提升为
`QUERY_OBSERVED`，补齐最新查询计划和实际命中别名。决策保存表名、物理维度
字段、规范值与别名、指标字段、业务 WHERE、参数化执行条件、LLM 模型和来源。
同义表达在成员治理阶段合并到同一规范成员，因此“智家”和“智家生态圈”只生成
一个规范决策；空值在调用 LLM、生成向量和写图之前被丢弃。

高基数、标识符型维度不会把几十万编码送往模型或向量服务。它们仍作为正式
DWS 维度加载到页面和问答范围，但成员匹配只允许精确值，避免无意义的相似
召回、成本膨胀和编码串错配。

资产管理中心的“维度值映射”页按正式维度展示，执行表下沉到每条决策：

```text
正式维度
  -> 维度描述:规范值
  -> 维度字段:规范值
  -> 指标字段 / 执行表
  -> 业务 WHERE / 参数化执行条件
```

页面首先读取全部 DWS 维度的聚合状态，因此即使某个维度尚未生成决策也会展示；
展开维度后再分页读取其真实决策，避免一次把数万条记录传到浏览器。页面同时
展示已加载成员、已生成决策、待处理向量和处理状态，不再用前端抽样的 200 条
结果反推维度总数。

LLM 调用失败会细分为租户配额不足、租户策略未授权、服务限流、超时、普通
调用失败或输出校验失败。后台使用租约和有限重试恢复临时失败；任何失败都不会
伪造“LLM 设计成功”，也不会把未验证策略写入决策图。

## 已修复故障：追问“其中的关键人才有多少”

故障计划 `3c598956-a8b9-463f-893c-9a061e73290e` 的
`conditions.dimensions=[]`，实际执行成整个员工范围的总人数。根因有三项：

1. 旧版 `ResolveQueryContext` 只恢复指标和单个维度编码，没有恢复上一轮
   `birth_cohort` 与 `employee_status` 成员条件。
2. `key_talent` 源字段是多标签组合，71 个成员中有 54 个包含完整
   “关键人才”标签；“关键人才”只命中维度名称，未形成过滤条件。
3. 关键人才维度与当前指标版本的兼容关系仍是 `PROPOSED`；而旧数据库触发器
   又没有在兼容关系变为 `VERIFIED` 时标记语义图待重建，导致关系即使验证后
   也可能暂时不进入执行图。

修复后第二轮条件是上一轮两项条件与 `key_talent` 受控集合的并集。真实物化表
直接核算与问答执行结果均为 `5,093` 人。迁移
`000134_semantic_compatibility_graph_event` 保证后续兼容关系增删改都会自动重建
语义图，不再依赖其他资产变更偶然触发。

## 上线验收

1. 导入并发布 DWD/DWS，完成物化。
2. 发布指标，刷新出生年代段、人员状态和小微编码维度成员。
3. 通过 `/api/v1/semantic-assets/import` 导入语义资产。
4. 等待语义图 `status=READY` 且 `appliedEventVersion=requestedEventVersion`。
5. 依次回归：
   - `80后小微在职人员有多少人？`
   - `其中的关键人才有多少？`（必须继承上一轮范围并返回 `5,093`）
   - `本月销售额和订单量分别是多少？`
   - `那上个月呢？`
   - `同时再加上退款金额`
6. 运行 `make lint`、`make build`、`make frontend-lint`、
   `make frontend-build` 和 `scripts/verify-semantic-qa.sh`。
