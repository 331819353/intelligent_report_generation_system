## 1. 为什么需要这份提案

`orchestrator.Loop` 每次调用只执行**一个认知阶段**（`LoopRequest.Stage`），返回一个 `Decision`。
要把一次提问从 `RECEIVED` 推到 `ANSWERED`，必须回答两个问题：

1. 每个阶段结束后，下一个阶段是什么；
2. 一个认知动作如何映射到 `askdata.question_runs` 的状态迁移。

**代码中不存在任何一处回答了这两个问题。** 已存在的是三张互不连接的约束表：

| 已有约束 | 位置 | 内容 |
|---|---|---|
| 运行状态图 | `askdata.valid_question_run_transition`（迁移 000247） | 哪些状态迁移合法 |
| 阶段 → 可用工具 | `orchestrator.allowedToolsForCognitionStage` | 每个阶段允许调用哪些工具 |
| 阶段 → 可用动作 | `cognition.stageAllowsAction` | 每个阶段允许模型返回哪些动作 |

本提案只做一件事：把这三张表**连接起来**，不新增权限，也不放宽任何门禁。

## 2. 提案的阶段—状态映射

下表左侧（状态、迁移）与右侧（阶段、动作）都取自上述既有约束，未作改动。

| 运行状态 | 认知阶段 | 由谁推进 | 该状态下允许的非工具动作 | 迁移目标 |
|---|---|---|---|---|
| `RECEIVED` | — | Worker（确定性） | — | `AUTHORIZED` / `BLOCKED` |
| `AUTHORIZED` | — | Worker（确定性） | — | `CONTEXT_READY` / `BLOCKED` |
| `CONTEXT_READY` | — | Worker（确定性） | — | `UNDERSTANDING` / `BLOCKED` |
| `UNDERSTANDING` | `UNDERSTANDING` | LLM | `Clarify`、`Block` | `RETRIEVING` / `CLARIFICATION_REQUIRED` / `OUT_OF_SCOPE` / `BLOCKED` |
| `RETRIEVING` | `CANDIDATE_JUDGMENT` | LLM | `ProposeBinding`、`Clarify`、`Block` | `BINDING` / `CLARIFICATION_REQUIRED` / `BLOCKED` |
| `BINDING` | `DISAMBIGUATION` | LLM | `ProposeBinding`、`Clarify`、`Block` | `GRAPH_VALIDATING` / `CLARIFICATION_REQUIRED` / `OUT_OF_SCOPE` / `BLOCKED` |
| `GRAPH_VALIDATING` | — | 确定性（图解析 + Bundle 校验） | — | `IR_READY` / `CLARIFICATION_REQUIRED` / `BLOCKED` |
| `IR_READY` | `PLAN_SELECTION` | LLM | `ProposePlan`、`Clarify`、`Block` | `PLAN_VALIDATING` / `BLOCKED` |
| `PLAN_VALIDATING` | — | 确定性（编译 + 计划校验） | — | `EXECUTING` / `BINDING`（有界纠错） / `CLARIFICATION_REQUIRED` / `BLOCKED` |
| `EXECUTING` | — | 确定性（执行） | — | `RESULT_VERIFYING` / `BLOCKED` |
| `RESULT_VERIFYING` | `ANOMALY_ANALYSIS` | LLM | `AnalyzeAnomaly`、`Clarify`、`Block` | `ANSWER_VERIFYING` / `BINDING`（有界纠错） / `CLARIFICATION_REQUIRED` / `BLOCKED` |
| `ANSWER_VERIFYING` | `RESULT_VERIFICATION` | LLM | `VerifyResult`、`Finalize`、`Clarify`、`Block` | `ANSWERED` / `BLOCKED` |

`CallTool` 在任何阶段都允许，且不改变状态——工具调用只在当前状态内消耗预算。

未在本表出现的三个阶段（`ASSET_REVIEW`、`FEEDBACK_ATTRIBUTION`、`RELEASE_REVIEW`）不属于问数运行链路，
分别服务报告资产认证、反馈归因与 Release 评审，保持独立。

## 3. 动作到迁移的固定规则

| 动作 | 迁移 | 说明 |
|---|---|---|
| `CallTool` | 停留在当前状态 | 由 Loop 预算约束；不产生状态迁移 |
| `ProposeBinding` / `ProposePlan` / `AnalyzeAnomaly` / `VerifyResult` | 推进到下一状态 | 提案内容先经确定性校验，校验失败按 `Block` 处理 |
| `Finalize` | `ANSWERED` | 仅 `ANSWER_VERIFYING` 允许；叙述必须先通过事实校验 |
| `Clarify` | `CLARIFICATION_REQUIRED` | 终态之一，等待用户应答后由新的 Run 继续 |
| `Block` | `BLOCKED` 或 `OUT_OF_SCOPE` | 由 `Block` 载荷的原因码决定，二者都是终态 |

## 4. 必须由你裁定的开放问题

以下三点无法从代码推导，需要产品/架构决定。这也是我没有直接实现的原因。

### 4.1 `UNDERSTANDING` 阶段缺少「完成」动作

`stageAllowsAction(StageUnderstanding, …)` 只允许 `CallTool`、`Clarify`、`Block`——
**没有任何动作表示「我理解完了，继续下一步」**。`RETRIEVING` 同理依赖 `ProposeBinding`，但
`UNDERSTANDING` 没有对应的提案动作。

可选方案：

- **A.** 新增 `ActionProposeUnderstanding`，与其他阶段保持一致（改动动作词表，需同步 schema）。
- **B.** 约定「模型不再调用工具即视为该阶段完成」，由 Worker 推进（不改词表，但把控制流藏在隐式约定里）。
- **C.** 让 `UNDERSTANDING` 与 `RETRIEVING` 合并为一个阶段，由 `ProposeBinding` 一次性收口。

我倾向 **A**：显式动作可审计，且与其余阶段同构；B 的隐式约定在回放审计时无法区分「完成」与「模型放弃」。

### 4.2 有界纠错的次数上限

状态图允许 `PLAN_VALIDATING → BINDING` 与 `RESULT_VERIFYING → BINDING` 两条回退边。
`Loop` 预算限制了工具与 LLM 调用总数，但**没有单独限制回退次数**，理论上可在预算内反复横跳。
建议显式约定上限（例如每个 Run 最多 2 次回退），并在超限时 `Block`。

### 4.3 报告引擎是否共用同一张表

AI-005 要求两条链路共用阶段协议。报告引擎当前用的是自己的
`IDENTIFY / ANALYZE / PLAN / DISPATCH` 四阶段（见 02 §2.1），与本表并不同构。
需要确认：是把报告引擎也迁到本表，还是把「共用」定义为共用**事件流与审计字段**、
而阶段名称各自保留。后者改动小得多，且不影响任何门禁。

## 5. 确认后的落地范围

本提案确认后，实现是机械的：

1. 在 `orchestrator` 中新增阶段协议表（本文件 §2、§3），配可执行测试逐条锁住映射；
2. 若采纳 §4.1 方案 A，扩展动作词表与 `cognition-action-v1` schema（含嵌入副本的漂移测试）；
3. `QuestionRunWorker`：领取 → 构造 `Binding`/`Registry`/`CognitionRunner`/`Loop` → 按协议驱动阶段
   → 心跳 → 释放；`ABANDONED` 领取直接终结为 `BLOCKED`（该分支已完全确定，可先行交付）。

在本提案确认前，Worker 的 `FRESH` 执行路径不实现——在 Worker 内部私自发明一套阶段顺序，
会与报告引擎产生第二套分叉协议，正是 [02 §3](./02_技术设计终稿.md) 明令禁止的
「只优化 Prompt 而不落入支柱治理」。
