# 智能问答指标定位链路

## 目标

用户问题必须先通过指标语义库补全含义并定位治理后的指标，再在该指标允许的维度
范围内匹配维度值，最后锁定指标版本绑定的精确数据集版本和 ACTIVE 物化。一个问答
轮次可以定位 1 到 8 个指标，并为每个指标生成独立 QueryPlan。LLM 只能通过工具复制
已发布指标编码或决策图 ID，不得选择物理表、拼接 SQL 或用维度值反向猜指标。

## 四阶段解析链路

1. **指标语义与指标定位**：LLM 先检索 `metric_semantic_documents`，用指标名称、
   别名、口径和说明补全完整问题；完成语义检索后才能检索当前 `PUBLISHED` 指标
   清单。模型只能复制清单候选编码，候选不足可以在有界循环内再次检索，候选并列
   时返回用户确认。
2. **维度语义与维值决策图**：指标版本先固定 `datasetVersionId`，再返回该指标
   在当前精确数据集版本上全部已验证、非敏感且可执行的兼容维度。维度常用词可以通过
   `semantic_term_assets` 映射到规范成员值，但只在该指标版本具有
   `VERIFIED` 且非 `UNSAFE` 兼容关系的维度中，以租户内成员值/别名索引做
   词法与向量混合匹配，再检索持久化决策图。模型只能复制决策 ID；同值跨维度
   或多成员无法唯一判断时返回用户确认。
3. **计划与数据检索**：模型结果只形成结构化条件文档。数据集由已发布指标版本
   的不可变绑定唯一确定，服务端固定同一语义图 generation，证明
   `指标 → 维度/成员 → 精确数据集版本 → ACTIVE 物化 → 上游血缘`，
   生成 path hash，并由可信编译器参数化生成查询。执行前再次核对版本、兼容关系、
   物化、权限和水位。
4. **结果与点评**：返回数据、条件和证据链；用户可提交准确/不准确评价。反馈按
   用户和查询计划持久化，只作为质量证据，不直接在线修改指标或维度资产。

## 决策图的存储模型

“收入 → 区域 → 日期 → 产业”及其不同提问顺序不分别保存为物理树，也不对
整条排列链路做向量化。若有 `n` 个维度，预生成所有排列会接近 `n!`，还会在
新增维度或成员时大面积失效。系统保存的是可复用事实，查询时动态形成决策 DAG：

- PostgreSQL 保存领域、指标版本、维度、成员、指标—维度兼容边和成员别名；
- `metric_semantic_documents` 只保存并向量化指标名称、别名和口径文本；
- `dimension_member_semantic_documents` 只保存并向量化非敏感、低基数、
  `FULL` 策略的维度成员值；
- pgvector HNSW 与规范化值/别名 B-tree、trigram 共同完成混合召回；
- 当前查询状态只含已选指标、已命中维度及剩余兼容维度。用户先说“产业”就先
  走产业分支，先说“区域”就先走区域分支，最终收敛到同一组规范条件；
- Redis 只适合缓存多轮会话的临时决策状态，不是权威目录；当前规模无需引入
  Neo4j。只有跨领域、多跳关系探索成为独立产品能力时才评估图数据库。

最终计划保存的不是 SQL，而是服务端生成的条件文档：

```json
{
  "domain": "运营",
  "metricCode": "income",
  "metricVersionId": "metric-version-id",
  "datasetVersionId": "dataset-version-id",
  "dimensions": [
    {
      "dimensionCode": "birth_cohort",
      "dimensionId": "birth-cohort-id",
      "memberKeys": ["80-85", "85-90"]
    },
    {"dimensionCode": "industry", "dimensionId": "industry-id", "memberKey": "food"}
  ],
  "timeRange": {"start": "2026-06-01", "endExclusive": "2026-07-01"}
}
```

数据库查询只能由受信编译器根据指标定义、字段合同和这份条件文档参数化生成。

## 排序与歧义规则

- 指标名称或编码精确命中优先；向量相似只能进入候选，不能直接成为结论。
- 同一维度命中多个不同成员时，只有明确的语义资产集合合同才生成参数化
  `IN`；普通同义词冲突仍返回 `MEMBER_AMBIGUOUS`，不会擅自缩减为一个值。
- 同一个成员值命中多个兼容维度时，只有问题明确包含唯一维度名称/编码才能
  消歧，否则返回 `MEMBER_AMBIGUOUS`。
- 不同维度各命中一个成员时可形成复合过滤，每个维度分别验证指标兼容关系。
- 多标签组合维度必须通过 `TAG:<规范标签>` 资产显式声明；解析器按逗号边界在
  当前有效成员中展开，最多 128 个成员，并继续逐成员证明兼容关系。
- 没有维度条件的纯指标问题跳过维值阶段，不为“所有、数量、总数、月份”等
  通用或时间语言制造成员过滤。

## 性能边界

| 阶段 | 上限/索引 | 说明 |
| --- | --- | --- |
| 指标候选 | Top 12 | 主表保证清单完整，语义文档和向量延迟不阻断精确名称查询 |
| 成员片段 | 最多 512 | 词法与成员值向量混合召回，不做成员全文外发 |
| 兼容维度 | 最多 32 | 先按精确指标版本、数据集版本和安全兼容边限域；超过上限作为目录治理问题处理 |
| 成员候选 | 最多 128 | 用于受治理集合与多标签展开；超出或无法唯一化即失败关闭 |
| 图路径 | 调用方与租户配置共同限制 | 默认最多 8 跳，且只读取单一 READY generation |

## 可观测性

问答编排使用显式状态机。规划成功链为 `RECEIVED → AUTHORIZED → CONTEXT_READY →
VALIDATING → PLAN_READY`；执行链继续经过 `COST_APPROVED → EXECUTING →
RESULT_VERIFIED → ANSWERED`。需要确认时进入 `CLARIFICATION_REQUIRED`，内部失败
进入 `BLOCKED`。运行和事件持久化在 PostgreSQL，只有 question hash 和安全状态，
不记录问题原文、隐藏推理、SQL 或结果行。

指标与维度工具调用共用有界 Evidence Loop。非终止步骤必须取得新的稳定证据 ID；
内核使用 `stateHash + toolName + argumentsHash + errorCode` 拦截空转和重复动作，最多
三轮。Provider 不可用、超时或限流才允许固定安全降级，协议错误与无进展不会被
静默隐藏。

`QueryPlan.resolution` 返回五个不含敏感原值的阶段：

- `INTENT_RECOGNITION`
- `DOMAIN_CATALOG`
- `METRIC_CATALOG`
- `DIMENSION_MEMBER`
- `DATASET_LOCK`

每一步记录状态、候选数、选中编码或稳定决策码。问题原文和成员原值不写入
计划；计划只保存 question hash、成员证据 ID、指标/数据集/物化版本和路径证据。
