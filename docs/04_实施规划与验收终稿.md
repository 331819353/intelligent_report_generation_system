## 1. 闭环判定口径

功能模块仅在同时满足以下条件时才算「完整可闭环」：有明确触发人/处理人/审批人/Owner；主路径可执行且不依赖手工改库；异常/拒绝/撤回/超时/降级有可见出口；关键写操作受权限/版本/幂等/审计约束；产物能被下游消费且失效时通知下游；结果有可量化验收标准。

实现状态四层口径：

| 层级 | 定义 |
|---|---|
| BE | 数据模型、领域服务、API/Worker 和自动化测试 |
| FE | 真实 API 接线的界面，不以 fixture/提示文案替代执行 |
| E2E | 真实数据库和应用进程上从触发走到终态，含一条异常支路 |
| BIZ | 真实 Owner、业务资产、黄金集、SLA 和目标环境签署 |

## 3. 一期实施路线

### 3.1 总顺序

```text
M1 数据建模收口 → M2 语义资产灌注 → M3 语义工作台与 Release ACTIVE
  → M4 报告主链（P11） → M5 报告资产进入对话（P12 + P09/P10）
  → M6 门禁、生产化与一期 BIZ 签署
```

「报告先行」是产品交付顺序；能力依赖链固定为 **数据建模 → 语义建模 → Release ACTIVE →（报告 | 问数）**：报告与问数是语义层的同级消费者，Release ACTIVE（M3 出口）同时解锁报告主链（M4）与问数语义查询路径；报告资产仅为问数的增强先验，不是问数的前置条件。

### 3.1.1 MVP 可提前验证的最短切片

上面的依赖链适用于**可反哺问数的报告**（组件必须为 `SEMANTIC_IR` 绑定）。但组件使用 `DATASET_FIELD` 绑定时，运行时只依赖已发布的 Dataset Version（见 [02 §6.1](./02_技术设计终稿.md) 与 `internal/report/runtime/plan.go`），**不需要 Release ACTIVE**。

因此报告主链可以在 M1 出口之后立即端到端验证，不必等待 M2/M3：

```text
数据源 → 数据集发布与物化 → 空白新建报告 → DATASET_FIELD 绑定 → 发布 → 运行/导出/分享
```

这条切片同时不依赖模型提供方（见 [06_HANDOFF §4.15](./06_HANDOFF.md)），是当前唯一无外部前置、可完整走通的业务闭环，应作为 MVP 的首个可演示目标。它不改变一期验收口径：报告资产要进入问数检索，仍必须满足 `SEMANTIC_IR` 绑定与 Release ACTIVE。

### 3.3 M2 语义资产灌注（P04～P07）

原则：**先导入、后页面；审批不代签**。

| 工作流 | 内容 | 任务 |
|---|---|---|
| S1 建设通道 | 批量导入（模板→行级校验→批次撤回）；可加性启发式建议与 Owner 补录清单 | IMPORT-*、ADD-002、HUMAN-008 |
| S2 首域资产 | 3～10 认证模型、20～50 指标（口径/Formula/可加性/时间/正反例）、20～40 维度（成员策略/层级/别名）、词典/P0 认证问法/1～3 个 KPI Bundle | 业务方输入门禁 |
| S2+ 业务补充信息 | 指标口径业务说明、维度值定义与组织信息、企业内部黑话/缩写、数据过滤规则的采集、导入与 Owner 认证 | SEM-CTX-001、HUMAN-015 |

## 6. 容量与灾备合同（摘要）

本节为容量与灾备的权威合同；可执行脚本在 `scripts/`（loadtest、askdata-postgres-backup/restore、askdata-graph-rebuild、verify-database），命令清单见 [06_HANDOFF §5](./06_HANDOFF.md)。

### 6.1 容量（OBS-003/OPS-007）

合同实现于 `internal/askdata/observability`（`CapacityReport` / `EvaluateCapacitySignability`），
运行器为 `scripts/loadtest`，报告 schema 为 `askdata-capacity-report-v2`。

- 压测配置**必填** `scopeProfile`。取值闭集：`P1_REPORT_ASKDATA`（一期）、`FULL_PLATFORM`（不阻塞一期，是超集而非替代）。
- **必测场景由 profile 决定**，缺一即拒绝运行：
  - `P1_REPORT_ASKDATA` = `FAST_PATH`、`COMPLEX_LOOP`、`WAREHOUSE_POOL`、`VECTOR_RECALL`、`GRAPH_3_HOPS`、`LLM_DEGRADATION`、`KPI_BUNDLE`、`PLATFORM_ACCESS`、`REPORT_RUNTIME`、`REPORT_PUBLISH`、`REPORT_EXPORT`。
    报告链路是一期产品的一半；只压问数却声称覆盖报告，得到的是另一个系统的容量结论。
  - `FULL_PLATFORM` = 上述全部 + `SUBSCRIPTION_DISPATCH`、`DECISION_WORKFLOW`。
- 开发机或单节点 Compose 结果不得冒充目标环境容量结论。报告携带 `signability`，
  缺任一签署输入时**固定** `POC_NOT_SIGNED` 并列出缺项；该结论在校验时**重算**，
  因此手工编辑报告改不出一份已签署的结论，并以 CRITICAL 级 `CAPACITY_POC_NOT_SIGNED` 告警呈现。
- 签署输入（缺一即 `POC_NOT_SIGNED`）：
  1. `scopeProfile`；
  2. `connectionBudgets`：API、AskData、报告 runtime、导出四个独立池的上限、admission limit、峰值占用与拒入计数——
     池之间必须互不饿死，拿不出四份预算就证明不了这一点；
  3. `faultInjection`：七项全部实际注入且**优雅降级**（返回稳定失败/降级码、`droppedTasks == 0`）。
     静默丢任务记为缺证而非延迟告警：吞吐再好也补不回一条丢失的任务；
  4. `resourceWatermarks`：资源水位样本；
  5. `signoff`：目标环境、业务 Owner、签署时间、证据引用、告警处置记录。
- 故障注入矩阵（闭集，增删即合同变更）：`API_INSTANCE_LOSS`、`WORKER_RESTART`、`CONTROL_DATABASE_FAILOVER`、
  `WAREHOUSE_TIMEOUT_OR_POOL_EXHAUSTION`、`OBJECT_STORAGE_UNAVAILABLE`、`GRAPH_UNAVAILABLE`、`PROVIDER_RATE_LIMITED`。
- 首期规模假设：≤20 租户、首期 1 业务域、检索文档 ≤20 万、日问数 2,000～10,000、峰值并发 20～50、已发布报告 ≤2,000；越过阈值触发架构复核告警。

### 6.2 灾备（OPS-004/OPS-007）

合同实现于 `internal/platform/disasterrecovery`（`DrillReceipt`），校验入口 `cmd/askdata-dr-drill`。

- 控制库 `platform/askdata/report` schema 必须从**同一一致恢复点整体恢复**。恢复顺序是闭集且顺序即合同
  （`OrderedDrillStages()`，可用 `askdata-dr-drill -stages` 打印）：
  `FREEZE_WRITES` → `RESTORE_CONTROL_DATABASE` → `VERIFY_MIGRATIONS_AND_RLS` → `VERIFY_FOREIGN_KEY_CLOSURE`
  → `VERIFY_IMMUTABLE_EVENT_HASHES` → `RESTORE_OBJECT_STORAGE`（只接受数据库已引用且 Hash 一致的对象）
  → `VERIFY_WAREHOUSE_SNAPSHOT_READONLY` → `REBUILD_SEARCH_AND_GRAPH_PROJECTIONS`（比对 Hash）
  → `RESTART_WORKERS_IN_TIERS` → `BUSINESS_SMOKE_AND_UNFREEZE`。
  迁移/RLS 未校验就查外键闭包证明不了任何事；业务冒烟前解冻则把演练变成事故。
- **失败即封顶**：任一阶段失败后，后续阶段不得记为成功。顺序存在的意义就是不让后面的检查被读成
  覆盖了前面没通过的那一步；跳步、乱序、缺阶段一律拒收受据。
- RTO 从故障发现算到**最后一个通过的**阶段（算到最后一个*尝试*的阶段等于把恢复时间记在失败的步骤上）；
  RPO 从恢复出来的最后一条持久业务事实算起，而不是从备份文件写完算起。二者由校验器重算。
- 受据携带 `signability`，缺目标环境、RTO/RPO 预算、任一阶段证据引用或 Owner 签署时固定 `DRILL_NOT_SIGNED`；
  超出自身声明的预算同样不可签署。
- 图重建演练：`scripts/askdata-graph-rebuild.sh`（只指向演练 Space，重放并比对投影证明）；
  备份/恢复：`scripts/askdata-postgres-backup.sh` / `askdata-postgres-restore.sh`
  （只接受空目标 + 显式确认，并比对恢复后的 Release 清单）。三者的输出即对应阶段的 `evidenceReference`。
- 备份「成功」不等于恢复「验收」；本地演练通过不代表目标环境达到业务 RTO/RPO——
  这正是本地运行只会得到 `DRILL_NOT_SIGNED` 的原因，而不是缺陷。

## 7. 一期 Go / No-Go

**Go**：首域 Release ACTIVE 且密封门禁通过；`E2E-P1-001` 在真实依赖上通过；报告主链与对话引用链 BIZ 签署；安全样本 100%；目标环境容量/灾备签署。

**No-Go 或暂停**：业务方无法提供 Owner/口径/黄金集；密封集 Wilson 下界 <95%；投影一致性无法保证；报告引用无法固定版本/组件/Hash；目标环境未提供。
